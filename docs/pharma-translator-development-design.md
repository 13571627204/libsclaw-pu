# 译言·药企 C 端内容翻译器开发需求与系统设计文档

文档版本：V1.0  
编制日期：2026-11-02  
适用范围：产品评审、UI/UX 设计、技术评审、研发排期、测试验收、部署交付  
工作名称：译言·药企 C 端内容翻译器（“译言/一言”最终品牌名待商务确认）

> 本文档把原始业务构想转换为可开发、可测试、可验收的技术需求。系统定位是“医学证据与合规辅助的内容生产工作台”，不替代医学部、合规部、法务部门或行政广告审查。AI 输出必须经过人工确认后才能流转，任何自动判断都不得表述为法律结论或发布保证。

---

## 1. 文档目标

本设计解决以下问题：

1. 把产品定位、七步业务流程和人工审批规则转换为明确的软件功能。
2. 统一产品、设计、前端、后端、算法、测试和实施团队的开发口径。
3. 明确当前仓库中六步确定性 MVP 与七步企业版目标之间的边界。
4. 给出系统架构、数据模型、接口、状态机、权限、审计、安全和测试方案。
5. 给出分阶段实施计划，避免一次性承诺尚无数据授权或规则来源的能力。

## 2. 产品目标与边界

### 2.1 产品目标

产品面向药企市场部、OTC 品牌经理、医学/学术部、合规部、运营团队、CSO 服务商及大健康品牌方，完成以下闭环：

```text
企业原始资料
  → 结构化产品档案
  → 卖点与医学证据验证
  → C 端生活场景翻译
  → 竞品内容洞察
  → 法规与平台规则过滤
  → 多平台内容生产
  → 多角色审批、导出与审计归档
```

核心价值：

- 能讲：把说明书术语翻译成用户能够理解的生活场景和语言。
- 能证：每项产品事实能够追溯到说明书、企业文献或经授权的权威资料。
- 能过：在发布前识别法规、平台规则和企业内部红线风险。
- 能追溯：每次输入、修改、生成、审批、返工和导出均留下版本及责任人记录。

### 2.2 不在系统承诺范围内

- 不承诺 AI 生成内容天然合法、有效或可直接发布。
- 不以模型推理代替医学证据，不允许用“常识”“业内都知道”补足证据。
- 不将估算关键词包装成真实搜索量或平台热度。
- 未获得平台授权时，不承诺实时抓取小红书、抖音、知乎、电商等数据。
- 不绕过平台访问控制、反爬机制、付费墙、版权或个人信息保护要求。
- 不自动向外部平台发布内容，除非后续单独完成授权、接口和发布审批建设。
- 不允许 RX 产品进入普通大众媒体营销内容路径；只能进入经企业确认的患者教育、用药陪伴或专业人员教育路径。

## 3. 需求冲突与统一决策

原始材料同时存在“七步全流程”和“六步操作流程”两套描述。研发统一采用以下口径：

### 3.1 企业版标准流程：七步

| 步骤 | 名称 | 主要责任角色 | 强制输出 |
| --- | --- | --- | --- |
| 1 | 产品档案建档 | 市场部/品牌经理 | 结构化档案、原文定位、档案快照 |
| 2 | 企业商品文献验证 | 医学部/学术部 | 卖点—证据—话术三联表、禁用卖点库 |
| 3 | 场景翻译引擎 | 市场部/品牌经理 | 3—5 个重点场景、关键词候选 |
| 4 | 竞品内容扫描 | 市场部+运营 | 数据来源清单、内容缺口、优先切口 |
| 5 | 合规过滤 | 合规部 | 风险清单、法规依据、处理结果、规则版本 |
| 6 | 批量内容生产 | 市场部+合规部 | 多平台内容包、素材建议、引用和风险状态 |
| 7 | 终审、导出与归档 | 品牌总监/业务负责人 | 发布授权、导出文件、完整审计链 |

### 3.2 当前代码基线：六步确定性 MVP

当前仓库已经实现一个可运行的六步 MVP：

| 当前 MVP 步骤 | 已实现内容 | 对应七步目标 |
| --- | --- | --- |
| 1 品名与说明书 | 文件校验、OCR/文本提取、8 个关键字段、人工确认 | Step 1 |
| 2 四维拆解 | 成分、主治功能、对症人群、背书、现有渠道、品牌名和产品名及安全约束；按药品名称检索本地药企知识库与搜索内容，经生成模型整理后人工确认 | Step 3 的前置拆解 |
| 3 场景生成 | 确定性场景、1—5 个场景选择、RX 限制 | Step 3 |
| 4 搜索词与优先级 | 来源可追溯的估算关键词 | Step 3 的关键词子模块 |
| 5 文献证据 | 基于说明书来源的 Claim、证据等级和医学确认 | Step 2 的基础版 |
| 6 内容与审批 | 草稿组装、硬规则扫描、市场/合规/终审和 JSON 导出 | Step 5、6、7 的基础版 |

当前 MVP 不得按企业版完整能力验收。目标开发应通过数据库迁移、角色隔离、文献库、竞品连接器、规则库和异步任务逐步升级为七步流程。

### 5.1 项目与工作台

| 编号 | 需求 | 优先级 |

| FR-PROJ-001 | 创建、搜索、筛选、查看和归档内容项目 | P0 |
| FR-PROJ-002 | 展示当前步骤、负责人、待办时长、风险数和版本号 | P0 |

### 5.2 Step 1：产品档案建档

必填字段：

- 商品名/药品名称和通用名；
- 批文类型；
- 产品类型；
- 剂型；
- 规格；
- 说明书功能主治/适应证原文；
- 用法用量；
- 禁忌与不良反应；
- 批准文号或注册/备案编号。

功能要求：

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S1-001 | 上传 JPG/JPEG/PNG/WEBP/PDF，校验扩展名、文件头、大小和可解码性 | P0 |
| FR-S1-002 | 提取关键字段并保留页码、原文、坐标、置信度和提取器版本 | P0 |
| FR-S1-003 | 左侧原文、右侧表单联动，字段可回到原文位置 | P1 |
| FR-S1-004 | 低置信度、缺失、冲突字段必须突出提示并人工确认 | P0 |
| FR-S1-005 | 关键字段为空、无来源或未确认时禁止流转 | P0 |
| FR-S1-006 | 同一 SKU 档案支持复用、迭代和历史版本 | P1 |
| FR-S1-007 | 多文件上传、排序、重复页识别、扫描 PDF OCR | P1 |

当前代码已支持单个图片/PDF、企业 OCR Provider、本地 RapidOCR、可选 Tesseract、人工校对文本和关键字段后端拦截；多文件和异步 OCR 属于后续建设。

### 5.3 Step 2：文献与卖点验证

卖点类型：成分、功效、人群、背书。证据等级：

- `STRONG`：一手、直接、可核验的证据；
- `WEAK`：间接、体外、样本或适用条件受限的证据，只能弱化表达；
- `NONE`：无证据，不允许进入后续内容。

功能要求：

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S2-001 | 上传 PDF、DOCX 等企业文献，记录版权、密级、版本、生效和失效时间 | P0 |
| FR-S2-002 | 文献解析为页、段落和切片，保留原文件定位 | P0 |
| FR-S2-003 | 从产品档案抽取 10—20 条候选卖点 | P0 |
| FR-S2-004 | 每条卖点匹配一个或多个证据片段，并显示匹配依据 | P0 |
| FR-S2-005 | 医学审核人可调整证据等级，但必须填写理由 | P0 |
| FR-S2-006 | 无证据卖点进入企业不可用卖点库 | P0 |
| FR-S2-007 | 输出卖点—证据—场景—话术三联/四联卡 | P1 |
| FR-S2-008 | 文献撤回、过期或权限变化时，标记所有受影响项目并要求重审 | P1 |
| FR-S2-009 | 无有效且医学确认的卖点时强制阻断 Step 3 | P0 |

技术约束：RAG 只负责召回候选证据，不自动把相似文本判定为医学成立；证据等级最终由医学审核人确认。

每个场景至少包含：名称、目标人群、时间、地点、触发事件、核心痛点、用户内心独白、搜索词、内容钩子、信任锚、允许卖点、禁用话题和证据覆盖率。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S3-001 | 仅使用 Step 2 已确认的强/弱证据卖点生成场景 | P0 |
| FR-S3-002 | 生成 8—12 个候选，用户选择 3—5 个重点场景 | P0 |
| FR-S3-003 | 支持强打、弱打、删除、编辑和单场景重新生成 | P1 |
| FR-S3-004 | 人群不得超出说明书或医学审核确认范围 | P0 |
| FR-S3-005 | 关键词显示来源、估算标记、平台、时间和优先级依据 | P0 |
| FR-S3-006 | 未接入授权数据源时必须显示“内部估算”，不得显示为真实热度 | P0 |
| FR-S3-007 | RX 只允许进入企业批准的专业教育或患者陪伴场景 | P0 |

| FR-S4-003 | 输出场景分布、内容公式、信任锚、价格带、用户高频痛点和样本量 | P1 |
| FR-S4-004 | 输出内容缺口及置信度，支持 P0/P1/P2 人工优先级 | P1 |

采集功能必须先完成法务、平台条款、个人信息和版权评审。首期可用“人工导入数据 + 来源声明”替代实时采集，不应以非授权爬虫作为验收前提。

### 5.6 Step 5：合规过滤

规则分级：

- `BLOCK`：直接阻断，不得审批和导出正式包；
- `CAUTION`：可生成草稿，但必须逐条人工处理；
- `SUGGESTION`：推荐替换或优化，不阻断；
- `PASS`：当前规则未识别明显风险，不等同于法律保证。

每条命中结果必须包含：规则 ID、版本、风险级别、命中文本、位置、适用产品类型、平台、法规/规则来源、条款、生效时间、处理建议、处理人和处理结果。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S5-001 | 规则按法律法规、部门规章、平台规则、行业标准和企业红线分类 | P0 |
| FR-S5-002 | 规则支持草稿、审核、发布、停用、生效/失效和历史版本 | P0 |
| FR-S5-003 | 每次扫描绑定不可变的规则集版本和检索日期 | P0 |
| FR-S5-004 | 风险定位到具体文本，并提供修改建议和前后对比 | P0 |
| FR-S5-005 | BLOCK 未关闭或 CAUTION 未处理时不得合规确认 | P0 |
| FR-S5-006 | RX 大众平台内容直接阻断并给出专用路径建议 | P0 |
| FR-S5-007 | 支持专家咨询单、授权范围、答复和附件留痕 | P1 |
| FR-S5-008 | 新规则发布后支持扫描历史内容并产生影响清单 | P2 |

法规和平台规则必须引用可核验的正式来源。原始需求中列举的法规、司法解释和版本仅作为候选清单，不能未经法务核验直接写入生产规则。

当前实现（合规过滤引擎）：

- 知识库建设方：中睿医药商学院，六层（法律法规、部门规章、平台规则、行业标准、司法解释与典型案例、更新与解读机制），通过 `GET /compliance/knowledge-base` 返回版本号、背书与更新机制。
- 三级规则：`block`（❌ 违规，直接拦截）/`caution`（⚠️ 谨慎，人工逐条复核）/`replace`（🟢 建议替换）；内容标签 `pass`/`caution`/`blocked`。RX 项目在大众平台直接拒绝生成，只走患者管理路径。
- 知识库检索 + 模型复核：`POST /projects/{id}/compliance/review`，检索中睿知识库与本地药企知识库，模型输出风险标记为 `source=ai`，须同样逐条处理。
- 专家答疑：`POST /projects/{id}/compliance/expert-tickets` 与 `.../{ticket_id}/answer`，24 小时时限 `due_at`。
- 合规确认：签字人本人、职务含“合规”、禁止代签；谨慎/替换项逐条决定（谨慎项须批注）；`citation_covered=true`；存在 block 或规则/知识库版本过期时拒绝并要求返工。审查记录写入 `approvals.compliance.record`（含 `kb_version`、`rule_version`、`retrieval_date`）。

### 5.7 Step 6：批量内容生产

支持的平台模板包括小红书图文/视频、抖音、视频号、公众号、朋友圈、电商详情页、评论区、私信 SOP、知乎/百度问答。首期平台范围以合同和配置为准。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S6-001 | 按平台、场景、数量、语气和周期创建生成任务 | P0 |
| FR-S6-002 | 每个事实句必须绑定已确认 Claim ID 和证据引用 | P0 |
| FR-S6-003 | 生成完成后自动执行 Step 5 规则扫描 | P0 |
| FR-S6-004 | 支持单条编辑、重新生成、批量调整语气和修改对比 | P1 |
| FR-S6-005 | 输出标题、正文、话题、素材建议、发布时间和问答建议 | P1 |
| FR-S6-006 | 市场和合规分别确认，二者均通过后才能进入终审 | P0 |
| FR-S6-007 | 修改已确认事实、卖点或高风险片段后自动撤销下游审批 | P0 |

生成过程必须采用结构化输出，并对模型返回执行 JSON Schema 校验、Claim 白名单校验和风险扫描。模型未返回 Claim ID 的事实句应被阻断，而不是由系统猜测绑定。

### 5.8 Step 7：终审、导出和归档

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-S7-001 | 终审清单检查档案、证据、竞品来源、风险、双审和审计链完整性 | P0 |
| FR-S7-002 | 仅授权总监/业务负责人可签发发布授权 | P0 |
| FR-S7-003 | 支持 JSON、Excel、Word/飞书或 CMS 格式；具体格式按阶段开放 | P0/P1 |
| FR-S7-004 | 导出包带项目、版本、内容 Hash、签署人、规则版本和生成时间 | P0 |
| FR-S7-005 | 未终审版本只能导出带水印的“审核草稿”，不可标记为可发布 | P0 |
| FR-S7-006 | 归档后普通用户只读，所有导出行为写入审计日志 | P0 |

## 6. 业务状态机

### 6.1 项目状态

```text
DRAFT
  → STEP_1_REVIEW
  → STEP_2_MEDICAL_REVIEW
  → STEP_3_SCENE_REVIEW
  → STEP_4_COMPETITOR_REVIEW
  → STEP_5_COMPLIANCE_REVIEW
  → STEP_6_MARKET_REVIEW
  → STEP_6_COMPLIANCE_REVIEW
  → STEP_7_FINAL_REVIEW
  → APPROVED
  → ARCHIVED
```

任意非终态可进入：

```text
REWORK → 指定当前或前置步骤
TERMINATED → 只读归档
```

### 6.2 步骤状态

- `LOCKED`：前置步骤未完成；
- `PENDING`：等待处理；
- `PROCESSING`：后台任务执行中；
- `IN_REVIEW`：等待人工确认；
- `PASSED`：确认通过；
- `REWORK`：已打回；
- `BLOCKED`：存在硬阻断；
- `TERMINATED`：项目终止。

### 6.3 状态转换规则

1. 后端是唯一状态机真源，禁止客户端直接提交 `current_step` 或审批状态。
2. 每次动作必须带 `project_version` 或 `If-Match`，防止多人覆盖。
3. 每个动作使用幂等键；重复请求不得产生重复审批或重复导出。
4. 返工到某一步时，该步骤及其下游产物标记失效，下游审批全部撤销。
5. 文献失效、Claim 变化、规则版本强制升级均可触发受影响步骤重新审核。
6. 终止操作必须填写原因，恢复终止项目需要管理员和业务负责人双重授权。

### 7.1 当前仓库技术基线

### 7.2 企业版推荐架构

```text
Vue Web 工作台
    │ HTTPS / JWT / SSO
    ▼
FastAPI API 层
    ├─ 身份、租户、RBAC
    ├─ 项目与七步状态机
    ├─ 文档/文献服务
    ├─ 证据与 Claim 服务
    ├─ 场景/竞品服务

### 8.1 核心实体关系

Project 1─N Document 1─N DocumentChunk

Project 1─N ContentItem 1─N ContentVersion
ContentVersion 1─N ComplianceFinding
Project 1─N Approval
Project 1─N AuditEvent

```

### 8.2 主要表

#### `organizations`

- `id`, `name`, `status`, `data_region`, `retention_policy_id`
- `created_at`, `updated_at`

#### `users` / `memberships`

- 用户身份与企业成员关系分离；
- 成员记录包含 `org_id`, `user_id`, `role_codes`, `department_id`, `status`；
- 角色变化写审计事件。

#### `products` / `product_versions`

- `products` 保存 SKU 稳定身份；
- `product_versions` 保存每次确认后的档案快照；
- 关键字段包含名称、通用名、批文类型、产品类型、剂型、规格、功能主治、用法用量、禁忌/不良反应、批准文号；
- 每个字段另存 `source_document_id`, `page_no`, `source_text`, `polygon`, `confidence`, `confirmed_by`, `confirmed_at`。

#### `projects` / `project_steps`

- `projects`：`id`, `org_id`, `product_version_id`, `name`, `state`, `status`, `version`, `owner_id`；
- `project_steps`：`project_id`, `step_no`, `status`, `assignee_role`, `started_at`, `completed_at`, `output_version`；
- 使用乐观锁字段 `version` 防止覆盖。

#### `documents` / `document_chunks`

- 文档记录来源、文件 Hash、密级、权限、版权说明、版本和有效期；
- 切片记录页码、段落、坐标、文本 Hash、解析器版本和嵌入版本；
- 删除采用“先失效、等待期后物理删除”，受审计保留期约束。

#### `claims` / `evidence_citations`

- Claim：`id`, `type`, `text`, `status`, `evidence_level`, `medical_confirmed_by/at`；
- Citation：`claim_id`, `document_id`, `chunk_id`, `page_no`, `quoted_text`, `relation`, `score`；
- `score` 只表示检索相关性，不等同于医学证据强度。

#### `scenarios`

- 保存目标人群、三要素、痛点、内心独白、钩子、关键词、允许 Claim ID、禁用话题、证据覆盖率和人工优先级。

#### `competitor_datasets`

- 保存数据来源、授权凭据引用、平台、采集时间、样本量、时间范围、导入文件 Hash 和置信度；
- 原始数据与分析结果分离保存。

#### `compliance_rules` / `rule_sets` / `findings`

- 规则记录 `rule_id`, `version`, `category`, `product_types`, `platforms`, `severity`, `matcher`, `source_uri`, `clause`, `effective_at`, `expired_at`, `status`；
- 发布的规则版本不可直接修改，只能创建新版本；
- Finding 绑定内容版本和规则版本，保存命中文本、位置、建议和处置结果。

#### `content_items` / `content_versions`

- 内容项保存平台、类型、场景、状态；
- 内容版本保存标题、正文、结构化片段、Claim 引用、模型、提示词模板版本、生成参数和内容 Hash；
- 人工编辑产生新版本，不覆盖旧版本。

#### `approvals` / `audit_events`

- Approval：步骤、角色、决定、意见、签署人、签署时间、业务版本和内容 Hash；
- AuditEvent：追加式存储 `event_type`, `actor`, `timestamp`, `object_type/id`, `before_hash`, `after_hash`, `metadata`；
- 审批记录不得由业务接口更新或删除。

## 10. AI、OCR 与检索设计

### 10.1 AI Provider Gateway

统一封装模型调用，记录：

- 模型提供方、模型名称和版本；
- 提示词模板 ID 和版本；
- 输入资料 ID，不在普通日志中保存敏感原文；
- 结构化输出、Token 用量、耗时和错误；
- 数据是否允许离开企业环境。

企业可以配置本地模型、私有化推理或经批准的云模型。未获授权的企业文献不得发送给公共服务，也不得用于供应商训练。

### 10.2 OCR

处理顺序：文件校验 → 病毒扫描 → 图片质量检测 → OCR/文本层提取 → 字段抽取 → 置信度融合 → 人工校对。

字段来源分为：

- `DOCUMENT_EXTRACTED`：来自文档文本层或 OCR，保留页码/坐标；
- `MANUAL_REVIEW`：用户粘贴或校对，必须标明人工来源；
- `MANUAL_INPUT`：用户新增，默认不能自动升级为强证据；
- `EXTERNAL_AUTHORIZED`：来自经授权数据源。

### 10.3 文献检索

检索流程：权限过滤 → 关键词/BM25 召回 → 向量召回 → 重排 → 返回候选段落 → 医学确认。所有引用必须能够回到原文件、页码和原文。撤回文献后相关引用立即失效。

### 10.4 内容生成防护

1. 只向模型提供当前项目允许的 Claim 和场景。
2. 要求模型返回句子级 `claim_ids`。
3. 校验 Claim 是否存在、已医学确认且未失效。
4. 执行产品类型和平台硬规则。
5. 执行合规规则扫描。
6. 将结果标记为“待人工审核草稿”。
7. 人工编辑后再次扫描；涉及事实变更时重新医学审核。

### 11.1 页面结构

一级导航：工作台、产品档案、内容项目、文献证据库、竞品洞察、合规中心、内容资产、审批中心、企业知识库、组织与设置。

## 12. 安全、隐私与审计

### 12.1 数据隔离

- 所有业务表和对象存储路径必须带 `org_id`。
- 后端查询强制注入租户范围，禁止仅由前端传租户 ID。
- 用户维度目录隔离仅适用于当前单机 MVP，不满足完整企业多租户要求。

### 12.2 文件安全

- 校验扩展名、MIME、文件头和实际解码结果；
- 限制文件大小、页数和压缩炸弹；
- 执行病毒/恶意文件扫描；
- 原文件和导出包采用静态加密；
- 下载使用短时签名地址或鉴权流式响应；
- 文件名必须清洗，防止路径穿越和响应头注入。

### 12.3 审计

必须记录：登录、查看敏感文献、上传、下载、字段修改、AI 生成、规则扫描、风险处置、审批、返工、终止、导出、权限变更和规则发布。

审计事件采用追加写，不允许普通业务接口修改。导出审计报告时计算内容 Hash，便于证明审批对象与导出对象一致。

### 12.4 数据生命周期

- 企业配置保留期限；
- 用户删除先进入等待期，等待期内可恢复；
- 法务保全、审计保留或已签署项目按策略保留；
- 到期清除数据库、对象存储、缓存和向量索引中的对应数据；
- 备份恢复后仍需执行删除墓碑同步。

- 前后端容器化部署；
- PostgreSQL、Redis、对象存储和 Worker 独立部署；
- 密钥进入 Secret Manager，不写入代码、镜像或日志；
- 内外网访问、模型出口和第三方连接器使用白名单；
- 配置数据库备份、对象存储版本、日志留存和告警；
- 支持本地化部署时，不默认依赖公网模型或公开搜索。

## 16. 测试设计

### 16.1 测试层级

- 单元测试：字段抽取、规则匹配、状态转换、权限和数据校验；
- 契约测试：前后端 DTO、错误码、分页、幂等和版本冲突；
- 集成测试：数据库、对象存储、任务队列、OCR、模型和向量检索；
- 安全测试：越权、跨租户、路径穿越、恶意上传、日志泄露和注入；
- E2E：OTC 主路径、RX 阻断、返工、文献失效、规则升级和终审导出；
- UAT：由市场、医学、运营、合规和总监分别使用独立账号完成。

### 16.2 必测主路径

1. OTC 说明书上传并确认产品档案。
2. 上传文献，建立至少一条强/弱证据 Claim，由医学角色签署。
3. 生成场景并选定 3—5 个重点场景。
4. 导入有来源说明的竞品数据并选择内容切口。
5. 执行合规扫描，处理谨慎项并验证阻断项不可绕过。
6. 生成不同平台内容，验证每个事实绑定 Claim。
7. 市场和合规双审、品牌终审、导出正式包和审计报告。
8. 任意步骤返工，验证下游审批撤销、版本保留和审计完整。

### 16.3 必测异常路径

- 空文件、伪造扩展名、损坏图片、超大 PDF、扫描 PDF 无文字；
- 关键字段为空、来源为空、未确认；
- 无证据卖点进入场景或内容；
- RX 选择小红书/抖音等大众平台；
- 规则命中后尝试直接终审；
- 无权限人员尝试医学、合规或终审；
- 两人同时编辑造成版本冲突；
- 模型超时、返回非结构化结果或伪造 Claim ID；
- 文献撤回后尝试导出旧内容；
- 竞品数据源失败或样本不足。

## 17. 验收标准与完成定义

### 17.1 P0 功能验收

- 七步状态机和角色权限在后端生效，不能越序或越权。
- 所有关键产品事实具有来源，所有可用 Claim 经过医学确认。
- 所有内容事实能够追溯到允许的 Claim 和文献片段。
- RX 大众营销、绝对化承诺、治愈/根治、无副作用等硬规则能够阻断。
- BLOCK 未关闭、CAUTION 未处理、双审未完成时不得终审。
- 返工保留旧版本并撤销受影响的下游审批。
- 终审导出包包含版本、规则集、签署人、引用和审计信息。
- 租户隔离、权限越权和恶意文件测试通过。

### 17.2 Definition of Done

一个需求只有同时满足以下条件才算完成：

1. 产品规则和异常行为有书面说明。
2. 前后端接口和类型一致，存在自动化契约测试。
3. 核心规则有单元测试，主路径有集成或 E2E 测试。
4. 权限、审计、幂等和并发冲突已处理。
5. 日志不泄露文献正文、密钥和个人敏感信息。
6. 用户界面包含加载、空、失败、重试和权限不足状态。
7. 操作手册、部署说明和验收用例同步更新。
8. 无 P0/P1 缺陷；遗留 P2 必须有双方确认的整改计划。

## 18. 分期开发计划

### 阶段 A：现有确定性 MVP 固化（已具备基础）

目标：形成可演示、可回归的单机版本。

- 单文件 OCR/文本提取；
- 8 个关键字段和来源追溯；
- 四维拆解、场景、关键词和基础 Claim；
- 基础硬规则；
- 六步顺序、返工、终止、版本快照；
- 市场、合规、终审流程的逻辑记录；
- JSON 交付包；
- 自动化测试。

### 阶段 B：企业基础版（建议第一合同交付范围）

目标：把单用户六步 MVP 升级为可供企业团队使用的七步系统。

1. PostgreSQL/对象存储迁移与组织级租户隔离；
2. 角色、部门、审批任务和独立账号签署；
3. 异步任务、进度、重试、幂等和乐观锁；
4. 文献上传、解析、全文检索、Claim—Citation 和医学审核；
5. 七步状态机及 Step 5/6/7 独立页面；
6. 规则版本、风险处置和审计报告；
7. Excel/JSON 导出；
8. 文件安全、备份、日志和监控。

### 阶段 C：数据与内容增强版

- 经授权的竞品数据连接器或标准导入；
- 场景缺口分析和样本置信度；
- 多平台结构化模板；
- 单条重生成、内容版本对比和素材清单；
- 飞书文档/多维表格集成；
- 专家咨询流程。

### 阶段 D：规模化与闭环

- CMS 和正式发布接口；
- 发布效果数据回传；
- 历史规则回扫和影响分析；
- 企业知识图谱；
- SSO、电子签名、灾备和更高可用部署；
- 基于真实反馈的数据分析与模板优化。

## 21. 需要业务方在企业版开发前确认的事项

1. 正式产品名是“译言”还是“一言”。
2. 首期交付是当前六步 MVP，还是必须改为完整七步界面和状态机。
3. 首期支持的产品类型、平台和内容模板清单。
4. RX 患者陪伴路径的法律依据、服务对象和允许内容范围。
5. 中睿合规知识库的真实数据格式、版权、更新责任、审核和签署机制。
6. PubMed、CNKI、万方等数据的账号、API、授权和引用方式。
7. 小红书、抖音、知乎、电商数据来源是否合法可用，能否使用人工导入替代。
8. 是否本地化部署，云模型是否允许接收企业文献。
9. 企业组织结构、角色兼任规则和电子签名要求。
10. 数据保留期、删除等待期、备份、灾备和审计保存期限。
11. Excel、Word、飞书、CMS 中哪些属于首期验收范围。
12. 性能、并发、可用性和服务器规格的合同指标。

在以上事项未确认前，研发应采用本文档中的安全默认值，并把依赖外部授权的数据能力标记为“待配置/待授权”，不得用模拟数据冒充真实生产数据。
